1. Product Overview
1.1 What Syntax Tree Is
Syntax Tree is a code intelligence platform that takes a codebase as input and produces a structured, queryable, visual understanding of that codebase. It reads source code mechanically, builds a verified knowledge graph of every entity and relationship, applies algorithmic and AI-driven analysis to identify architecture, components, and patterns, and presents the results through interactive visualizations, generated documentation, and a natural language query interface.
Every insight the system produces is traceable back to specific lines of code. The system is honest about uncertainty, carries confidence scores on every interpretation, and clearly separates mechanical facts from AI-generated interpretations.
1.2 Core Design Principle: Facts vs. Interpretations
The non-negotiable foundation of the entire system is the separation between facts and interpretations. Facts are what the code IS: function signatures, call relationships, import chains, class hierarchies. They are extracted mechanically by parsers with no AI involvement, and they are deterministic. Interpretations are what the code MEANS: component groupings, architectural patterns, design violations. They are generated by AI agents reasoning over verified facts, and they carry confidence scores, cite their evidence, and can be wrong.
This separation is the immune system of the product. The AI never fabricates structural relationships. It only reasons on top of verified ground truth. When it makes a claim, that claim is traceable through an evidence chain to actual lines of code.
1.3 Target Users
New developers joining a codebase who need to build a mental model of unfamiliar code in minutes rather than weeks.
Tech leads doing architecture review who need to see all architectural layers, boundary violations, data flow bottlenecks, and plan refactoring work.
Senior developers making changes who need to assess change impact, trace code paths to database tables, and track architectural decay over time.
1.4 What This System Is NOT
Not a code generator. It reads, understands, and explains. It does not write or modify code.
Not a linter. It does not check code against rules or style guides.
Not a replacement for developer judgment. It shows its work so humans can agree, disagree, or dig deeper.
Not a real-time IDE plugin. It is a batch analysis tool with incremental update capability.
Not magic. The AI agents produce interpretations that can be wrong. The system makes them auditable rather than mystical.
2. System Architecture
2.1 Four Subsystems
The system is composed of four major subsystems arranged in a strict pipeline. Each subsystem builds on the one below it, communicates through defined data contracts, and has no knowledge of the internals of its neighbors.
Subsystem A: Extraction Engine
Everything that touches raw source code and produces structured facts. Contains the Tree-sitter wrapper, all language adapters (Python, JavaScript, TypeScript, Go, Java, Rust), infrastructure parsers (SQL migrations, Dockerfiles, Kubernetes manifests, environment files), and the reference resolver. Also contains file discovery and classification. Takes a directory path as input and produces a complete ParseResult as output containing every node, every edge, every resolved call, every unresolved call site, and statistics about what succeeded and what failed.
Subsystem B: Knowledge Graph
The storage and query layer. Takes ParseResults from the extraction engine and loads them into dual SQLite + NetworkX storage. Exposes a query API that handles both property queries (give me all exported functions in this module) and graph traversals (give me everything reachable from this node within N hops). This is the central nervous system: everything upstream writes to it, everything downstream reads from it. SQLite is the persistent source of truth; NetworkX is a derived acceleration structure for graph traversal. The graph stores both facts and interpretations, but every node and edge carries metadata that identifies which it is.
Subsystem C: Intelligence Layer
The four AI agents: Clustering, Architecture, Documentation, and Query. They all follow the same contract (plan, execute, validate, commit) and interact with the system the same way: read from the knowledge graph, write interpretations back to the knowledge graph. The agents have a dependency order: clustering runs first, then architecture, then documentation. The query agent runs on demand in response to user questions. Each agent starts with algorithmic analysis before involving the LLM. The LLM names, describes, and synthesizes; it does not discover structure.
Subsystem D: Interface Layer
The API server and frontend. The API exposes REST endpoints for graph data, agent results, and documentation, plus WebSocket for streaming query responses. The frontend has three integrated surfaces: Monaco code viewer, React Flow graph viewer, and documentation viewer. They share a state management layer that coordinates bidirectional navigation. A view projection module transforms the raw graph into visualization-specific shapes (architecture view, dependency view, call flow, data flow, ERD).
2.2 Data Flow
Source code enters the extraction engine, which produces ParseResults. ParseResults are loaded into the knowledge graph. The intelligence layer reads from the graph, runs analysis, and writes interpretation nodes and edges back. The interface layer reads from the graph (both facts and interpretations) and renders visualizations, documentation, and query answers. Every downstream layer depends only on the graph API, never on the internals of any upstream layer.
2.3 Orchestration
A sequential pipeline coordinates the full analysis run. When a user points the tool at a codebase, the pipeline executes: extraction, graph loading, clustering agent, architecture agent, documentation agent, then signals the frontend that results are ready. Each stage either completes and produces a result, or fails and produces an error report. The pipeline stores checkpoint state so that if an agent fails, the graph retains all prior work. The tool does not support concurrent modifications during analysis; it is a batch process with a progress indicator. Incremental re-analysis is a separate operation triggered explicitly by the user.
2.4 Communication Contracts
Subsystems communicate through defined data structures, not shared internals. The extraction engine produces ParseResult objects. The knowledge graph exposes a typed query API. The agents write interpretation nodes and edges through the same API. This means any subsystem can be modified, optimized, or replaced without affecting its neighbors, as long as the contracts are honored.
3. Subsystem Design Details
3.1 Extraction Engine Internals
File discovery walks the target directory, classifies each file by language or type (Python, TypeScript, SQL migration, Dockerfile, K8s manifest, env file), and routes it to the correct adapter. Language adapters use Tree-sitter to parse source files into abstract syntax trees and extract: function and method declarations (name, parameters, return type, line range, visibility, decorators, docstring), class and struct declarations (name, fields, methods, parent classes, interfaces), module-level variables and constants, import statements, and call sites (unresolved references to function names with module hints from imports).
The reference resolver runs after all files are parsed. It takes the full set of call sites and resolves them against the full set of function definitions by tracing import chains and following language-specific module resolution rules. Resolved calls become CALLS edges with confidence "certain." Unresolved calls are logged for transparency. The resolver implements two layers for the initial build: explicit import tracing and module resolution. Heuristic matching and cross-language linking are deferred but the schema accommodates them.
Error handling follows a graceful degradation philosophy. Tree-sitter is error-recovering and produces partial trees for syntactically broken files. The parser extracts what it can from valid regions, marks nodes from error regions, reports parse errors in statistics, and never stops the pipeline for individual file failures.
3.2 Knowledge Graph Internals
The graph stores nodes (code entities, infrastructure entities, interpretation entities) and edges (structural, behavioral, data flow, infrastructure, interpretation relationships). Each node has a qualified name as its primary identifier (e.g., python:src/payments/service.py::PaymentService.processPayment), which survives minor code edits since it is not tied to line numbers. Line numbers are metadata used for display and navigation.
SQLite stores the full property set of every node, indexed for fast lookup by name, file, type, and full-text content search. NetworkX stores the graph topology in memory for fast traversal. Synchronization follows a strict contract: SQLite is written first inside a transaction, then NetworkX is updated. If SQLite fails, NetworkX stays unchanged. On startup, NetworkX is rebuilt from SQLite. The graph API hides the dual storage behind a unified interface so that consumers never interact with SQLite or NetworkX directly.
Interpretation nodes carry mandatory metadata: confidence score, evidence (list of factual node IDs that justify the interpretation), source tag ("inferred" vs "parsed"), and the model version that produced it. Edge types for cross-language linking (EXPOSES_ROUTE, FETCHES_ROUTE, CALLS_RPC) are defined in the schema even though the linker is deferred from the initial build.
3.3 Intelligence Layer Internals
Shared LLM Interface
A thin shared infrastructure layer handles API connection management, rate limiting, retry on transient failures, model version tracking, and cost logging. Each agent owns its own prompt engineering, output parsing, and validation logic above this shared layer. The shared layer is an HTTP client with retry and logging; agent-specific prompt templates, response schemas, and validation rules live within each agent module.
Clustering Agent
Runs Louvain community detection on a weighted call graph projection (inheritance: 4.0, direct calls: 3.0, co-location: 2.5, imports: 2.0, same directory: 1.0). Supplements with entry point tracing from decorators and route handlers. Refines clusters (subdivide over 50 nodes, evaluate under 3 for merging, compute cohesion and coupling scores). If cohesion falls below threshold, retries with different resolution parameters across three settings and selects the best. Sends cluster structural summaries to the LLM for naming and description only. Validates that cited entities exist and rejects generic names. Writes component nodes and BELONGS_TO_COMPONENT edges to the graph.
Architecture Agent
Analyzes the component interaction graph through eight lenses: structural dependencies (algorithmic, no LLM), domain language (semantic naming analysis), infrastructure shape (Dockerfiles, K8s manifests), resilience patterns (retry logic, circuit breakers), data gravity (shared database tables, data transforms), temporal patterns (cron jobs, queue consumers), security boundaries (auth, validation locations), and code hygiene (TODOs, convention violations). Each lens produces observations. The LLM synthesizes across all lenses, reporting dominant architectural style, subsystem boundaries, layer structure, violations, and discrepancies between intended and actual architecture. Every claim references specific findings from specific lenses.
Documentation Agent
Generates structured documentation at four levels: system overview, subsystem, component, and key function documentation. Receives structured context (function signatures, class skeletons, relationship summaries, cohesion metrics) rather than raw code. Output follows a defined schema with title, summary, body, code references, diagram references, confidence, and parent-child section relationships. Every paragraph links to graph nodes. Staleness detection stores hashes of referenced code nodes; changed nodes flag sections for regeneration.
Query Agent
Handles four query types: navigational (search graph by name/type/content and rank results), explanatory (semantic search, expand via graph neighborhood, LLM synthesis with citations), impact (traverse incoming dependencies transitively, score by dependent count and criticality, LLM summarizes blast radius), and architectural (pull architecture graph, pattern match against known styles, LLM assesses with evidence). Runs on demand in response to user questions, not as part of the batch pipeline. Every answer cites specific graph nodes.
3.4 Interface Layer Internals
The API layer serves graph data, agent results, and documentation through REST endpoints, with WebSocket streaming for query agent responses. View projections transform the raw graph into visualization-specific shapes. The architecture view aggregates function-level nodes to component level showing inter-component edges. The dependency view shows modules and import relationships. The call flow view traces from a starting function forward through its call chain. Data flow and ERD views project through data-related and database-related edges respectively. Heavy layouts (force-directed for large graphs) compute on the backend; simpler layouts (hierarchical for call flows) compute on the frontend.
The frontend has three surfaces sharing a state management layer. Monaco code viewer provides syntax highlighting, line numbers, search, and bidirectional linking to the graph. React Flow graph viewer renders interactive, zoomable, filterable visualizations across multiple view types. Documentation viewer renders structured generated documentation with live code references and embedded graph diagrams. Clicking a node in any surface navigates the other two surfaces to the corresponding context.
4. Project Phases & Build Plan
The project is built depth-first per language and bottom-up per layer. Each phase produces a complete, production-quality subsystem before the next phase begins. Within each phase, work is organized into discrete tasks, each producing a working, tested module. No MVP approach: each component is built to its full specification the first time.
PHASE 1
Foundation: Extraction Engine & Knowledge Graph
This phase builds the two subsystems that everything else depends on. The parser must be solid and the graph must be reliable before any intelligence runs on top of them. This is the longest phase and deliberately so: errors here propagate through every downstream layer.
Task 1: Graph Storage Layer
Data models for Node, Edge, CallSite, Component, Subsystem, and ParseResult. SQLite schema with indexes for name, file, type, and full-text search. NetworkX integration with synchronization contract. CRUD operations, graph traversal API, save/load, full test suite. The graph API is the contract that every other module depends on; it must be complete and stable before proceeding.
Task 2: Python Language Adapter
Tree-sitter wrapper with Python-specific AST extraction. Functions, classes, methods, imports, call sites, decorators, docstrings. Fixture files with exact expected outputs for every extraction type. This is the reference implementation that all subsequent language adapters will follow.
Task 3: TypeScript Language Adapter
Same extraction interface, TypeScript AST node types. Handles TypeScript-specific constructs: interfaces, type annotations, enum declarations, module exports. Uses the Python adapter as the reference for behavior and test structure.
Task 4: Infrastructure Parsers
SQL migration parser using sqlparse for tables, columns, and indexes. Dockerfile parser (regex-based) for base images, dependencies, and exposed ports. Kubernetes manifest parser (YAML-based) for services, deployments, and config maps. Environment file parser for variable names. Each produces nodes that enter the same knowledge graph through the same API.
Task 5: Reference Resolver
Layer 1 (explicit import tracing) and Layer 2 (module resolution) for Python and TypeScript. Converts call sites into CALLS edges by following import chains and language-specific module resolution rules. Reports unresolved references with context for debugging. This is the bridge between "what names appear in the code" and "what actually connects to what."
Task 6: Pipeline Orchestration
File discovery and classification. Sequential execution: parse all files, build graph, run resolver. Statistics and error reporting. The SyntaxTree.from_directory() entry point that takes a path and produces a fully populated knowledge graph. Progress reporting for the frontend to display during analysis.
Phase 1 Exit Criteria
Correctly identifies 95%+ of functions and 90%+ of function calls in a test corpus
Handles files up to 10k lines without errors
Processes 100k LOC codebase in under 5 minutes
Graph storage under 500MB for 100k LOC
Query response time under 100ms for graph traversals
Handles malformed code without crashing; clear error messages for unsupported files
PHASE 2
Intelligence: AI Agents
This phase builds the four agents that transform the raw knowledge graph into meaningful architectural understanding. Each agent follows the same contract (plan, execute, validate, commit) and each starts with algorithmic analysis before involving the LLM. Agents are built in dependency order: clustering first, then architecture, then documentation. The query agent is independent.
Task 7: Clustering Agent
Louvain community detection with weighted edge projection. Entry point tracing from decorated route handlers. Cluster refinement with cohesion and coupling scoring. Multi-resolution retry when cohesion is low. LLM labeling of algorithmic clusters. Validation of labels against actual graph structure. Component node creation with evidence references and confidence scores.
Task 8: Architecture Agent
Component interaction graph construction. Eight-lens analysis: structural dependencies, domain language, infrastructure shape, resilience patterns, data gravity, temporal patterns, security boundaries, code hygiene. Per-lens observation generation. Cross-lens synthesis by LLM with contradiction detection. Subsystem identification, layer detection, pattern recognition, violation detection. Quality scores that flow forward from clustering confidence.
Task 9: Query Agent
Intent classification across four query types (navigational, explanatory, impact, architectural). Graph query strategy selection per intent type. Context assembly from graph traversal results. LLM reasoning with mandatory citation of graph nodes. Response formatting with traceability links. This agent runs on demand, independent of the batch pipeline.
Task 10: Documentation Agent
System-level, subsystem-level, component-level, and key-function-level documentation generation. Structured output schema with title, summary, body, code references, diagram references, and confidence. Staleness detection via code node hash tracking. Section regeneration when referenced code changes. Importance scoring for selecting which functions receive detailed documentation.
Phase 2 Exit Criteria
Clustering agent identifies components with 80%+ precision against manual labeling
Architecture agent correctly detects 5+ common patterns
Documentation agent generates descriptions rated 7/10+ for accuracy by human reviewers
Query agent answers 70%+ of test questions correctly
Hallucination rate under 5% (all AI claims backed by graph evidence)
Agent confidence scores correlate with accuracy (r > 0.7)
PHASE 3
Interface: API & Frontend
This phase builds the surfaces through which users interact with the system. The API layer serves graph data and agent results. The frontend renders three integrated views that all trace back to source code.
Task 11: API Layer
REST endpoints for graph node and edge queries, component and subsystem data, architecture analysis results, and generated documentation. WebSocket endpoint for streaming query agent responses. View projection module that transforms the raw graph into visualization-specific subgraphs: architecture view (component-level aggregation), dependency view (module imports), call flow view (function call chains), data flow view (function-to-database paths), and ERD view (table relationships). Backend layout computation for large graphs.
Task 12: Frontend Integration
Monaco code viewer setup with syntax highlighting, line numbers, search, and graph linking. React Flow graph viewer with five view types, zoom, pan, filter, and search. Documentation viewer with structured rendering, live code references, and embedded graph diagrams. Shared state management layer coordinating bidirectional navigation across all three surfaces. Click a graph node and the code viewer jumps to that function. Click a function in the code viewer and the graph highlights its architectural position. Click a documentation reference and the code viewer opens at that line.
Phase 3 Exit Criteria
Frontend loads in under 2 seconds; graph rendering starts in under 500ms
Renders graphs with 1000+ nodes without lag
Supports 4 view types: architecture, dependency, call flow, data flow
All nodes clickable and linked to source code
Graph-to-code navigation works in under 1 second
Works on Chrome, Firefox, Safari (latest versions)
Responsive design on screens 1280px and wider
PHASE 4
Hardening: Validation, Expansion & Polish
This phase validates the complete system against real-world codebases, expands language support, and hardens the product for reliability and scale.
System Validation
End-to-end testing against a reference suite of real repositories: one small and clean, one medium and messy, one large and complex. Upload-to-graph pipeline validated for the 50k LOC in under 3 minutes target. Full user story walkthroughs: new developer onboarding, tech lead architecture review, senior developer change impact assessment. Usability testing targeting a new-user-to-first-graph time of under 5 minutes with no tutorial.
Language Expansion
Go, Java, and Rust language adapters following the established adapter pattern and using the Python and TypeScript adapters as reference implementations. Reference resolver extensions for each new language's module resolution rules. Validation against language-specific test corpora.
Incremental Updates
Detect changed files since last analysis run. Re-extract only changed files. Diff the graph to identify changed factual nodes. Find interpretation nodes whose evidence includes changed facts. Flag stale interpretations and re-run affected agents on the relevant subset. This builds on the evidence-based dependency tracking already present in the interpretation metadata.
Scalability & Reliability Hardening
Handle repositories up to 500k LOC. Support concurrent analysis of 5+ repositories. Ensure no critical security vulnerabilities via SAST scanning. Achieve 70%+ test coverage for core modules. Complete documentation that is tested and maintained.

6 languages supported: Python, JavaScript, TypeScript, Go, Java, Rust
Handles repositories up to 500k LOC
Supports concurrent analysis of 5+ repositories
Incremental updates re-parse only changed files
Staleness detection flags 90%+ of outdated documentation
New user can upload and view a graph in under 5 minutes (no tutorial)
Test users rate overall UX 7/10 or higher
Test coverage 70%+ for core modules; no critical security vulnerabilities
5. Cross-Cutting Concerns
5.1 Error Handling Philosophy
Individual failures never crash the pipeline. A file that cannot be parsed produces a warning. A call that cannot be resolved produces an unresolved marker. A cluster that the LLM cannot name gets a generated placeholder. An agent that fails leaves prior work intact in the graph. The system degrades gracefully and reports honestly about what it could not do.
5.2 Quality & Confidence Propagation
Every interpretation carries a confidence score and an evidence list. When downstream agents consume upstream interpretations, they factor in the upstream confidence. Low-confidence clustering produces low-confidence architecture produces documentation that honestly reflects uncertainty. Quality scores flow forward through the pipeline, never getting inflated.
5.3 Staleness Tracking
Every generated artifact stores hashes of the code nodes it references. When the graph updates due to re-analysis, sections whose referenced nodes have changed are flagged stale and queued for regeneration. Documentation is either current or honestly marked as outdated. There is no silent decay.
5.4 Traceability
Every graph node carries file path, line start, and line end coordinates into the source. Every AI-generated claim cites specific graph nodes as evidence. Every visualization element links to its underlying graph data. The chain is always: AI claim, graph evidence, specific code lines. Nothing in the system floats free of its source.
5.5 Testing Strategy
Each task produces a test file that serves as the specification. Tests use fixture files with exact expected outputs for deterministic modules (parsers, resolver, graph operations). Agent tests validate against manually labeled reference repositories. Integration tests verify contract compliance at subsystem boundaries. End-to-end tests validate complete user story workflows against real codebases.
